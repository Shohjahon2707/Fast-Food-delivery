# Запуск и размещение веб-MVP

## Локально

`python start.py`; сайт http://127.0.0.1:8000/ . База `db.sqlite3` и `media/` остаются на компьютере. `python start.py --setup-only` подготавливает файлы без запуска сервера. Для администратора используйте `manage.py createsuperuser` в окружении .venv.

Для резервной копии остановите сервер/диспетчер и скопируйте db.sqlite3 и media. Восстановление сначала проверьте в отдельной папке проекта. Не коммитьте пользовательскую базу.

## Публичная демонстрация — отдельная задача

1. Выбрать сервер с постоянным диском: SQLite нельзя держать на исчезающей файловой системе. Сохранить исходную базу компьютера отдельной копией.
2. Установить зависимости, выполнить `python scripts/compile_translations.py`, `python manage.py migrate` и `python manage.py collectstatic --noinput`.
3. Задать переменные DJANGO_DEBUG=false, уникальный DJANGO_SECRET_KEY, DJANGO_ALLOWED_HOSTS, CSRF_TRUSTED_ORIGINS и путь MEDIA_ROOT. `.env.example` — образец, Django читает окружение процесса; файл .env сам по себе не загружается.
4. Настроить HTTPS и публикацию /media/. Для одного небольшого SQLite-демо начать с одного процесса gunicorn; нагрузку измерить отдельно.
5. Если демонстрируется автоматическое распределение курьерам, запустить `python manage.py dispatch_orders` под process manager. Для одного только клиентского интерфейса это не условие просмотра и оформления.
6. Настроить SMTP для реальной отправки писем восстановления. По умолчанию письма только в локальной консоли.
7. Проверить регистрацию, фильтр, оформление, права, перезапуск и восстановление. Проверить `python manage.py check --deploy`.

Боевой сервис, внешний платёжный провайдер и домен этим MVP не подключаются автоматически. Наличная оплата отмечается сотрудником после фактического получения.
